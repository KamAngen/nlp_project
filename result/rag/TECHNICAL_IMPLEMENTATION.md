# Legal RAG Pro - 核心技术实现解析

本文档详细拆解了 Legal RAG 项目中各个核心任务（Task）的技术选型、架构设计与底层实现技巧。本项目旨在构建一个针对法律垂直领域的高性能、支持热更新的混合检索增强生成系统（RAG）。

---

## 🏗️ 整体架构设计原则

1. **多模态知识融合**：将法条（文本）、案例（关系）、常识（概念）进行异构存储与统一检索。
2. **硬件级性能压榨**：针对苹果 M 系列芯片（M4 Max）深度定制，启用 MPS (Metal Performance Shaders) 加速和半精度（bfloat16/float16）推理。
3. **不停机热更新**：支持增量数据的异步向量化与图谱动态扩张，无需重启服务或全量重建索引。

---

## 🎯 Task 1: 基础深度语义检索 (Dense Retrieval)

### 需求挑战
传统的基于关键词的检索（如 BM25）无法理解法律条文的语义重叠。例如，“非法集资”与“非法吸收公众存款”在字面上不同，但在法律事实上高度相关。

### 技术实现
*   **模型选型**：采用 `Qwen/Qwen3-4B` 大语言模型作为 Embedding 引擎的基础底座，利用其巨大的参数量来捕获极度微妙的中文法律语义。
*   **硬件加速技巧**：
    *   在 `embedding.py` 中，通过 `torch.backends.mps.is_available()` 自动探测苹果 M 系芯片，将模型张量强制分配至 `mps` 设备。
    *   使用 `torch_dtype=torch.bfloat16` 加载权重，使得 8GB 的模型能在不爆显存的前提下满载运行，同时将计算速度提升 2 倍以上。
*   **向量索引构建**：
    *   底层使用 `faiss` 或 PyTorch 原生的张量矩阵乘法进行暴力搜索（Brute-force Exact Search），保证召回的绝对准确性。
    *   实现了 `add_records` 增量构建逻辑，使得内存中的 `document_embeddings` 张量矩阵可以动态 `torch.cat()` 拼接扩展。

## 🎯 Task 2: 混合检索与重排 (Hybrid Search & Reranking)

### 需求挑战
纯语义检索容易出现“过度联想”（如查询“刑法264条”，它可能召回一堆不相干的盗窃案）。我们需要结合精确的字面匹配，并对最终结果进行高精度的二次审视。

### 技术实现
*   **双路召回 (Dual-stream Retrieval)**：
    1.  **Lexical 词法路**：基于 BM25 算法进行精确的字面 Token 匹配。
    2.  **Dense 语义路**：基于 Qwen-4B 的密集向量空间余弦相似度匹配。
*   **RRF (Reciprocal Rank Fusion) 融合技巧**：
    *   在两路召回后，不是简单相加分数（因为分数尺度不同），而是根据它们在各自列表中的**排名**计算 RRF 分数：`score = 1.0 / (K + rank)`。
    *   这保证了无论在哪一路排名前列的文档，都能在融合后获得高权重。
*   **Cross-Encoder 交叉编码器重排**：
    *   **难点**：双路召回的结果依然是初步的。
    *   **实现**：引入 `BAAI/bge-reranker-base` 模型。它不同于普通的向量模型，它将 Query 和 Document 拼接成一句话 `[CLS] Query [SEP] Document [SEP]` 送入模型，利用深度 Transformer 的 Cross-Attention（交叉注意力机制）进行逐词的交互比对。
    *   **输出标准化**：提取 `logits[0]` 后，通过 `Sigmoid` 激活函数将无界的标量分数强制压缩至 `0~1` 之间的置信度区间，方便前端渲染。
*   **短文本检索的定向优化 (Short-Text Retrieval Optimization)**：
    *   **痛点**：用户经常输入极短的 Query（如“死刑”、“法条264”）。对于短文本，其在稠密向量空间中含有的语义特征极少，传统的纯 Embedding 极易发生“语义漂移”或失效。
    *   **优化策略**：当检测到 Query 短于特定长度或包含高频确切词时，系统高度依赖 BM25（词法路）的硬匹配能力作为补充。随后的 Cross-Encoder 重排能够将被 BM25 强行捞回来的文档与短 Query 重新建立字级别的 Attention 联系，有效弥补了短文本在全局语义空间中的先天缺陷。

## 🎯 Task 3: 知识图谱动态构建与可视化 (Graph RAG)

### 需求挑战
法律案件不是孤立的文本，案件之间通过共同引用的“法条”产生了极强的拓扑关联。需要在检索结果外，为用户提供一张可解释的关联网络。

### 技术实现
*   **后端拓扑建模 (`graph.py`)**：
    *   采用 `NetworkX` 构建无向图。设计了两类实体节点：`case` (案件) 和 `statute` (法条)。
    *   当案件 A 和案件 B 都引用了“刑法第264条”时，图中就形成了一条 `案件A <-> 法条 <-> 案件B` 的天然二级联通路径。
    *   通过自定义的 `get_related_cases` 方法，利用广度优先搜索（BFS）深度遍历相邻节点，挖掘隐式案例。
*   **前端 Cytoscape 可视化 (`index.html`)**：
    *   引入 `Cytoscape.js` 引擎。
    *   **COSE 物理力导向布局**：弃用死板的网格布局，采用 `cose` (Compound Spring Embedder) 布局。节点之间产生互斥力，连接的边产生弹簧拉力，使图谱自然散开并聚类。
    *   **视窗自适应技巧**：在布局 `stop` 回调钩子中触发 `cy.fit()`，并通过 `mapData` 线性映射节点的物理像素大小，防止图谱因为节点文本过长而无限膨胀撑破视窗。

## 🎯 Task 4: 异步防抖与高并发热更新 (Hot Update)

### 需求挑战
当用户批量导入数百条甚至是数千条 JSON 案例时，向量化模型需要极大的计算资源。如果采用同步阻塞请求，会导致前端 504 甚至后端 OOM。此外，反复导入相同数据会导致索引无限膨胀。

### 技术实现
*   **FastAPI Background Tasks 异步调度**：
    *   在 `/update_batch` 接口中，主线程只负责接收数据并生成 UUID `task_id`，立刻返回 202 状态码给前端。
    *   将繁重的 Embedding 运算压入 `BackgroundTasks`。
*   **微批处理与显存保护 (Micro-Batching)**：
    *   设置 `chunk_size = 32`。这意味着哪怕用户导入一万条数据，后端也只会以 32 条为一组，切片喂给 Qwen-4B 模型，在显存极限边缘疯狂试探但绝不溢出。
*   **防呆去重逻辑 (Upsert Deduplication)**：
    *   在 `service.py` 中，插入内存前执行严格的 `record_id` 存在性检验。
    *   摒弃了危险的 `file.write(append)` 模式，采用**全量内存重写 (Full Rewrite)** 策略持久化到 `JSONL` 文件，彻底杜绝脏数据的产生。

## 🎯 Task 5: 智能课程采样 (Smart Curriculum Sampling)

### 需求挑战
传统的题库抽取是纯随机的，无法照顾到用户的当前水平。系统需要根据用户的“掌握度”动态调配题目难度，同时兼顾用户指定的主题（如：“只抽非法集资的题目”）。

### 技术实现
*   **混合检索构建候选池 (Hybrid Retrieval + RRF Fusion)**：
    *   当用户输入主题时，抛弃了早期版本中单一粗糙的纯语义过滤。现在直接引入“词法 + 语义”的混合检索算法，通过计算 RRF 分数来精准召回 Top-60 作为候选池。这确保了抽取的题目在“字面精确度”和“语义相关性”上都死死咬住指定的主题。
*   **难度动态加权 (Weighted Random Sampling)**：
    *   设计了非线性的 `_question_weight` 评分函数。
    *   当用户的掌握度 `mastery < 0.35` 时，系统将 `difficulty == 'easy'` 的题目权重暴力乘以 `100`。
    *   使用 `random.choices` 配合自定义的权重数组进行**无放回加权抽样**。最终呈现的结果就是：虽然带有随机性，但低水平用户抽到简单题的概率具有压倒性优势。
